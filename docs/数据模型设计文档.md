## 1. 设计目标与约束

### 1.1 业务场景

电商订单数据具有三个鲜明特征：

1. **生命周期明确**：订单创建后经历「待支付 → 已支付 → 已发货 → 已完成 / 已取消」的状态流转，通常 30 天内会被反复查询（用户查看、客服处理、售后），超过 30 天则查询频率骤降，主要用于对账、审计、年度统计。
2. **写多读杂、冷热分化**：热数据是高频小批量点查与多条件组合查询；冷数据是大批量顺序扫描与周期性统计。
3. **字段结构多态**：订单包含商品、收货地址等天然的内聚子结构，且不同品类商品的扩展字段不一致。

### 1.2 设计目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 热数据（近 30 天）支持毫秒级多条件点查与聚合 | 按 userId / status / 时间范围+goodsId 查询 P95 < 50ms |
| G2 | 冷数据（30 天以上）支持按时间范围的大批量顺序扫描 | 10 万条历史订单按月份扫描 < 3s |
| G3 | 冷数据支持按订单 ID / 用户 ID 的等效点查，不得退化为全表扫描 | 点查走索引表，单次 2 次 RPC 内完成 |
| G4 | 支持按月/按用户的统计类查询 | 指定月份总数量与总支付金额一次扫描完成 |
| G5 | 数据生命周期自动管理 | 迁移任务可幂等重跑，两库不丢数据、不永久重复 |
| G6 | 两库共用一个实体模型，避免字段口径分裂 | 单一 `Order` POJO 同时映射两边结构 |

### 1.3 关键约束

- **C1 单机伪分布式环境**：RegionServer 与 Mongo 均单节点，无热点压力，但设计须保留可水平扩展的余地。
- **C2 不使用 HBase 协处理器**：实验环境不便于部署 Coprocessor，二级索引必须用「索引表 + 应用层维护」实现。
- **C3 归档后订单基本只读**：状态流转只发生在热库，冷库以追加为主。
- **C4 不允许丢数据**：任何迁移/清理动作都必须先保证目标库写入成功。

### 1.4 访问模式清单（设计的唯一依据）

> 数据模型由访问模式驱动，而不是由字段清单驱动。下表是本设计全部决策的来源。

| 编号 | 访问模式 | 频率 | 作用库 | 关键谓词 |
|---|---|---|---|---|
| A1 | 按订单 ID 查订单详情 | 高 | 热 + 冷 | `orderId = ?` |
| A2 | 按用户 ID 查该用户所有实时订单 | 高 | 热 | `userId = ?`，按 orderTime 倒序 |
| A3 | 按订单状态查实时订单 | 中 | 热 | `status = ?`，按 orderTime 倒序 |
| A4 | 按时间范围 + 商品 ID 查实时订单 | 中 | 热 | `orderTime ∈ [from,to) AND goods.goodsId = ?` |
| A5 | 近 7 天各状态订单数与总支付金额 | 低 | 热 | `orderTime >= now-7d`，GROUP BY status |
| A6 | 按时间范围批量扫描历史订单 | 中 | 冷 | `orderTime ∈ [from,to)`，全字段 |
| A7 | 统计指定月份历史订单总数量与总支付金额 | 低 | 冷 | `orderTime ∈ [月初,次月初)` |
| A8 | 按用户 ID 批量查该用户全部历史订单 | 中 | 冷 | `userId = ?`，按 orderTime 倒序 |
| A9 | 查某用户全部订单（实时 + 历史） | 中 | 双库 | `userId = ?` |
| A10 | 归档：把 30 天前的热数据搬到冷库 | 定时 | 双库 | `orderTime < now-30d` |

- **基础信息组**：`orderId, userId, goodsId, goodsName, unitPrice, quantity, orderTime, channel` —— 一旦写入不再变化，查询时几乎总要读。

### 3.3 行键（RowKey）设计 —— 本设计的核心

#### 3.3.1 候选方案与对比

| 方案 | RowKey 形式 | 支持 A6/A7（时间范围扫描） | 支持 A1（按订单 ID 点查） | 支持 A8（按用户查） | 结论 |
|---|---|---|---|---|---|
| S1 | `<orderId>` | ❌ 只能全表 Scan | ✅ 直接命中 | ❌ 全表 Scan | 不满足 G2/G3 |
| S2 | `<orderTime 正序>+<orderId>` | ✅ 顺序扫描 | ❌ 需索引 | ❌ 需索引 | 可用，但"最近订单优先"要反向遍历 |
| **S3** | **`<19位倒序毫秒时间戳>\|<orderId>`** | ✅ 顺序扫描 | ❌ 需索引 | ❌ 需索引 | **✅ 采纳** |
| S4 | `<盐前缀>+<倒序时间戳>+<orderId>` | ⚠️ 需拆成 N 段扫描再归并 | ❌ 需索引 | ❌ 需索引 | 本实验无热点，徒增复杂度（见 §9） |

#### 3.3.2 采纳方案（S3）

```
RowKey = reverseTs(orderTime) + "|" + orderId

其中  reverseTs(t) = String.format("%019d", Long.MAX_VALUE - t)   // t 为毫秒时间戳
```

**示例**

| 订单 | 下单时间 | 时间戳 t | reverseTs(t) | RowKey |
|---|---|---|---|---|
| 20240612000123 | 2024-06-12 10:23:11 | 1718162591000 | 9223372035136614807 | `9223372035136614807\|20240612000123` |
| 20240612000124 | 2024-06-12 10:23:12 | 1718162592000 | 9223372035136614806 | `9223372035136614806\|20240612000124` |
| 20230301000007 | 2023-03-01 00:00:07 | 1677600007000 | 9223372033046775807 | `9223372033046775807\|20230301000007` |

#### 3.3.3 设计理由

1. **时间即前缀，范围扫描直接命中 RowKey**（满足 G2/A6/A7）
   HBase 的 RowKey 按字典序排列。`%019d` 保证倒序时间戳定宽 19 位、无前导零歧义，因此**字符串字典序 == 时间先后倒序**。同一月份的订单在物理上连续存放，按月的范围扫描（A7）只读连续的若干 HFile 数据块，是顺序 IO；而如果 RowKey 以 `orderId` 开头，同月订单会被打散到整张表，只能退化成全表 Scan（违反 G2）。

2. **倒序而非正序，让"最新订单优先"零成本**（相对 S2 的改进）
   A2/A3/A8 都要求「按 orderTime 倒序返回」。倒序时间戳让**字典序最小的行就是最新的订单**，Scan 从 startRow 顺序向前读即可天然得到"最新优先"，无需 HBase 端反向扫描（HBase 原生不支持高效逆序 Scan）、也无需在客户端把整段结果拉到内存再排序。

3. **保留 `orderId` 后缀，保证唯一性与可读性**
   RowKey 必须唯一。理论上同一毫秒可能有多笔订单，追加 `orderId` 后唯一性由业务主键保证；同时 RowKey 中带业务号，`hbase shell` 里排查问题时一眼能看出是哪笔订单。

4. **不使用 32 位哈希做定长时间戳**
   若用 `Integer.MAX_VALUE - epochSecond`（10 位秒级），同一秒内的大量订单会共享时间前缀、靠 orderId 排序，无法保证同秒内的时间精度；毫秒级 19 位在 10 万级数据量下体积代价可忽略（每行多 5 字节）。

#### 3.3.4 时间范围的 RowKey 映射（实现要点）

因为时间越晚 → `reverseTs` 越小，**区间的方向是反的**：

```java
// 查询 [from, to]（含两端）的历史订单
String startRow = reverseTs(to);                  // 时间大 → 值小 → 起点
String stopRow  = reverseTs(from) + "\uFFFF";     // 覆盖 from 那一毫秒的全部行（开区间）
Scan scan = new Scan()
        .withStartRow(Bytes.toBytes(startRow), true)
        .withStopRow(Bytes.toBytes(stopRow), false);
```

`"\uFFFF"` 的 UTF-8 编码为 `EF BF BF`，字节序大于 `"|"`（`0x7C`），因此 `reverseTs(from) + "\uFFFF"` 大于所有形如 `reverseTs(from) + "|" + orderId` 的行，能完整包含 `from` 这一毫秒的订单而不会多读。**这一点必须有单元测试断言**（构造边界订单：恰好在 `from` 和 `to` 毫秒），否则极易出现"少查一条/多查一条"的隐蔽缺陷。

### 3.4 列族参数说明

| 参数 | 取值 | 为什么这样设 |
|---|---|---|
| `VERSIONS` | `1` | 归档订单写入后不再修改（C3），保留多版本只会让同一单元格存多份旧值、放大存储与扫描体积。若业务确实需要留痕，应在应用层写审计表，而不是靠 HBase 多版本。 |
| `BLOOMFILTER` | `ROW` | 按订单 ID 点查（A1）是高频操作。行级布隆过滤器能让 Get 在不含该 RowKey 的 HFile 上直接跳过，显著减少随机读的 IO 次数。行级（而非 `ROWCOL`）已足够，且索引体积更小。 |
| `COMPRESSION` | `NONE` | 订单以 `goods_name`、`detail` 等文本为主，理论上 Snappy 压缩比可达 2~3 倍且解压开销低于 GZIP；但**本实验环境的 Hadoop 3.3.6 自带 `libhadoop.so` 未编译 Snappy 支持**（`hadoop checknative` 输出中无 snappy 项，`nm -D libhadoop.so` 查不到任何 snappy 符号，系统也未安装 `libsnappy.so`）。一旦列族设为 `SNAPPY`，RegionServer 在 MemStore 刷盘时即抛 `UnsatisfiedLinkError: NativeCodeLoader.buildSupportsSnappy()Z`，进而 `DroppedSnapshotException` 并反复 abort，表现为"只有 HMaster、没有 HRegionServer、表建不出来"。故本环境取 `NONE`：既不引入 native 依赖，也让写入/查询性能对比只反映存储引擎差异、不被压缩 CPU 开销干扰。**在支持 native Snappy 的环境里，把 `HBaseUtil` 中 4 处 `Compression.Algorithm.NONE` 改回 `SNAPPY` 即可**，其余代码无需改动。 |
| `TTL` | `FOREVER`（不设） | 历史订单需要长期保留用于对账与审计，**不设 TTL**。若业务规定只保留 3 年，可设 `TTL=94608000`（3×365 天），由 HBase 自动清理。 |
| `BLOCKSIZE` | `65536`（默认） | 范围扫描场景下默认块大小较均衡；若单行特别宽（>4KB）可调大到 128KB 减少索引项。 |
| `IN_MEMORY` | `false` | 历史数据不常驻内存，避免挤占 BlockCache。 |
| **列族数量** | **3 个** | **关键设计点**：HBase 的 MemStore 与 Flush 以列族为单位。把字段按访问模式分成 3 组，使得"只查支付信息"（A5 聚合）时不必读取庞大的 `logistics` 地址列族，减少实际 IO 量。但列族也不宜再多——每个列族一次 Flush 会产生更多小文件、放大压缩与合并开销，**3 个是本场景的合理上限**。 |

> **`status` 冗余在两个列族的原因**：A3（按状态筛选）需要连同 `orderTime` 一起判断，A6（按时间范围全字段扫描）需要连同地址一起返回。把 `status` 同时放进 `pay` 与 `logistics`，可以让"筛选 + 读地址"和"筛选 + 读金额"两条路径都不产生跨列族补读。代价是状态更新时要写两个列族（同一行内，成本可接受）。

### 3.5 预分区（Pre-splitting）

单 Region 会在写入阶段成为瓶颈（所有写都落在一个 RegionServer 上，且触发热点 Split）。本设计**按月份边界预分区**：

```java
// 假设数据覆盖 2024-01 ~ 2024-12，分割点为各月 1 号的倒序时间戳
byte[][] splits = {"2024-02-01","2024-03-01",...,"2024-12-01"}.stream()
        .map(m -> Bytes.toBytes(reverseTs(parseFirstMs(m))))
        .toArray(byte[][]::new);
admin.createTable(tableDesc, splits);
```

**为什么按时间分区而不是按哈希加盐**：冷数据的主要负载是时间范围扫描（A6/A7）。按时间预分区后，一次月度扫描只落在 1~2 个 Region 上，扫描是连续的；而加盐会把同月数据散布到全部 Region，范围扫描必须拆成 N 段再归并，得不偿失（详见 §9 备选方案）。

**分区边界的可维护性**：由于数据天然按月聚合，新增月份只需 `admin.split()` 或提前把边界一次配足（例如配到 2026-01），不必在读路径上做任何适配。

### 3.6 索引表 `order_history_idx`

单列族 `f`（`VERSIONS=1`、`BLOOMFILTER=ROW`、`COMPRESSION=NONE`），列 `f:rk` 存放主表 RowKey。两类索引行用前缀区分，互不冲突：

| 索引行 RowKey | 列 | 支撑访问模式 | 查询实现 |
|---|---|---|---|
| `ID#<orderId>` | `f:rk` | A1（按订单 ID 查详情） | `Get("ID#"+orderId)` → 取 `f:rk` → `Get(mainRk)` |
| `U#<userId>#<reverseTs(orderTime)>#<orderId>` | `f:rk` | A8（按用户查全部历史订单） | `Scan(withStartRow("U#"+uid+"#"), withStopRow("U#"+uid+"#\uFFFF"))` → 批量 Get 主表 |

**设计说明**

1. **为什么需要 `ID#` 索引**：主表 RowKey 以时间开头，无法直接 `Get(orderId)`（违反 G3）。索引表把 `orderId` 还原成可直接点查的键，代价是 A1 由 1 次 RPC 变为 2 次 RPC。这是"时间范围扫描"与"主键点查"两个不可调和的诉求之间的必要妥协。
2. **为什么 `U#` 索引把 `reverseTs` 放在 `userId` 之后**：`userId` 作为等值前缀定位到该用户的全部索引行，`reverseTs` 紧随其后保证**同一用户的行按时间倒序排列**，那么"取该用户最近 N 条历史订单"只需在 Scan 上设 `setLimit(N)`，不必读全部结果再排序。
3. **为什么两个索引共用一张表**：两类索引行的 RowKey 前缀不同（`ID#` / `U#`），字典序上不会交错，可以放在同一张表里。共用一张表减少了 Region 数量与运维成本；若访问量与生命周期差异很大，也可拆成两张表（见 §9 备选方案）。
4. **索引一致性由写入方保证**：主表 `Put` 与索引表 `Put` 必须**在同一个批量提交中一起完成**（先主表、后索引），迁移任务必须等两者都 `flush()` 成功后才允许删除 MongoDB 中的源数据（约束 C4）。

### 3.7 单行存储量估算

| 项 | 估算值 | 说明 |
|---|---|---|
| RowKey | 34 B | 19 位时间戳 + `\|` + 14 位订单号 |
| 单元格数量 | 19 个 | 见 §3.2 |
| 数据净荷 | ≈ 190 B | 各列值合计（中文按 UTF-8 3 字节/字计） |
| KeyValue 元数据开销 | ≈ 19 × 30 B ≈ 570 B | 每单元格含 rowkey、列族、限定符、时间戳、类型等头部开销 |
| **单行原始大小** | **≈ 800 B** | 未压缩 |
| **单行实际占用** | **≈ 800 B** | 列族不压缩（`COMPRESSION=NONE`，原因见 §3.4）；若环境支持 Snappy，此值可降到约 300 B |
| 索引表每订单 2 行 | ≈ 200 B | 每行 RowKey + 1 个单元格 |

| 数据规模 | 主表 | 索引表 | 合计（未压缩） |
|---|---|---|---|
| 1 万条 | ≈ 8 MB | ≈ 4 MB | ≈ 12 MB |
| 10 万条 | ≈ 80 MB | ≈ 40 MB | ≈ 120 MB |
| 1000 万条 | ≈ 8 GB | ≈ 4 GB | ≈ 12 GB |
| 1 亿条 | ≈ 80 GB | ≈ 40 GB | ≈ 120 GB |

10 万级数据（本实验要求）在单机伪分布式上占用量极小，一次月度扫描（约 8000 行）预期的 IO 量仅约 6 MB，这是 A7 能在秒级完成的基础。

## 4. MongoDB 集合设计

### 4.1 集合 `order_real_time`

只存放近 30 天的实时订单，30 天以上由归档任务迁移至 HBase。

### 4.2 文档结构（样例）

```json
{
  "_id": ObjectId("666b1f2c8a3d4e5f60718293"),
  "orderId": "20240612000123",
  "userId": NumberLong("100234"),
  "goods": {
    "goodsId": "G00087",
    "goodsName": "无线蓝牙耳机",
    "unitPrice": NumberDecimal("299.00"),
    "quantity": 2,
    "category": "数码"
  },
  "payAmount": NumberDecimal("578.00"),
  "coupon": NumberDecimal("20.00"),
  "channel": "APP",
  "status": "已支付",
  "orderTime": ISODate("2024-06-12T10:23:11.000Z"),
  "payTime": ISODate("2024-06-12T10:25:40.000Z"),
  "address": {
    "province": "广东省",
    "city": "深圳市",
    "detail": "南山区科技园路 1 号",
    "receiver": "张三",
    "phone": "138****0000"
  },
  "createTime": ISODate("2024-06-12T10:23:11.000Z"),
  "updateTime": ISODate("2024-06-12T10:25:40.000Z")
}
```

### 4.3 文档模型设计理由

1. **订单是聚合根，商品与地址内嵌而非引用**
   电商订单中，商品与地址是**随订单一起读取**的内聚子结构（A1/A6 都要一次拿到全貌），几乎不存在"查某地址下的所有订单"这类反向查询。采用内嵌文档后，一次 `find` 即可返回完整订单，避免了关系型数据库中"订单表 + 商品表 + 地址表"的三表 JOIN；同时内嵌文档与订单在同一个文档页中，读放大最小。

2. **内嵌不等于不能查**
   内嵌的 `goods.goodsId` 依然可以建立索引并作为查询条件（A4），MongoDB 对点号路径的原生支持使内嵌结构不会损失查询能力。这一点与 HBase 需要精心设计 RowKey 形成鲜明对比，也是"实时检索用 MongoDB"的核心理由。

3. **`_id` 与 `orderId` 并存**
   `_id` 由 MongoDB 自动生成的对象 ID，是物理主键，用于分片与内部寻址；`orderId` 是业务主键，迁移时用于与 HBase 对齐、以及保证幂等去重。二者职责不同，必须都存在（并用唯一索引约束 `orderId`）。

4. **金额使用 `Decimal128` 而非 `double`**
   金额是精确数值，`double` 的二进制浮点误差会在聚合求和时累积（A5 要统计总支付金额）。`Decimal128` 是 MongoDB 原生的十进制类型，与 Java `BigDecimal` 语义一致。代价是聚合时不能直接 `$sum`，需 `$toDecimal`/`$toDouble` 转换——这是本设计有意接受的代价。

5. **`updateTime` 保留**
   状态流转（A3）只发生在热库，保留更新时间便于排查"状态何时变更"和识别长期停留在「待支付」的异常订单。

### 4.4 索引设计

**设计方法：ESR 原则（Equality → Sort → Range）**
复合索引字段顺序应依次为：等值匹配字段、排序字段、范围匹配字段。这样 MongoDB 可以先用等值前缀精确定位，再借助索引本身的顺序满足排序（避免内存排序），最后在索引上完成范围过滤。

| 索引名 | 定义 | 支撑访问模式 | 设计说明 |
|---|---|---|---|
| `uk_order_id` | `{ orderId: 1 }`，`unique: true` | A1、A10 | 业务主键唯一约束；同时作为归档去重与按订单号点查的入口 |
| `idx_user_time` | `{ userId: 1, orderTime: -1 }` | A2、A9 | `userId` 等值 + `orderTime` 排序，完全符合 ESR：等值前缀定位该用户，索引内天然倒序，`find` 无需额外排序阶段 |
| `idx_status_time` | `{ status: 1, orderTime: -1 }` | A3、A5 | 等值 `status` + 排序 `orderTime`。A5 聚合的 `$match: {orderTime: {$gte: ...}}` 是范围条件，落在索引的第二个字段上仍可高效利用（前缀 `status` 等值 + 后缀范围扫描），无需为聚合单独建索引 |
| `idx_goods_time` | `{ goods.goodsId: 1, orderTime: -1 }` | A4 | A4 的谓词是「时间范围 + 商品 ID」，其中 `goodsId` 等值、`orderTime` 范围。按 ESR 必须把等值字段放前（`goodsId` 等值选择性更高），时间作为范围字段收尾，索引仍可完整覆盖 |

**索引数量与写放大的权衡**
上表共 4 个索引。MongoDB 每插入一条文档都要同步维护全部索引，写放大与索引数量近似成正比。之所以没有为 `city`、`channel` 等字段再建索引，是因为它们**不在任何已知访问模式的谓词中**——索引必须由访问模式驱动，而不是"给所有字段都加上"。这一取舍直接影响第 5 章的写入性能对比结论。

**索引验证方式**
每个索引建立后，用 `explain("executionStats")` 确认查询计划为 `IXSCAN`（走索引）而非 `COLLSCAN`（全集合扫描），并记录 `totalKeysExamined` 与 `nReturned` 的比值接近 1，说明索引选择性良好。explain 输出截图作为设计验证证据附入报告。

### 4.5 为什么不对 `order_real_time` 设置 TTL 索引

MongoDB 的 TTL 索引可以按 `orderTime` 自动删除 30 天前的文档，看似正好满足"热数据只留 30 天"，**但本设计明确不使用**：

1. **TTL 删除与归档任务存在竞争**。TTL 后台线程每 60 秒扫描一次并直接删除文档。如果某次归档任务失败或延迟，TTL 已经把源数据删掉，数据将**永久丢失**（违反 C4）。
2. **TTL 无法保证「先写 HBase 成功再删 Mongo」的顺序**。数据生命周期管理必须由应用层显式控制，而不能交给一个不可观测、不可重试的后台机制。
3. **TTL 删除无法记录审计信息**（删了多少、什么时候删的），不利于实验中的耗时统计与结果验证。

因此，30 天前的数据**只由归档任务按批次显式删除**，删除动作发生在 HBase 写入并 `flush()` 成功之后。

## 5. 双库分工与数据生命周期

### 5.1 分工逻辑

| 维度 | MongoDB `order_real_time` | HBase `order_history` |
|---|---|---|
| 数据范围 | 近 30 天 | 30 天以上全量历史 |
| 数据量级 | 总量的 ~60%（可配置） | 总量累积增长 |
| 访问模式 | A1~A5：点查、多条件组合、聚合统计 | A6~A8：时间范围大扫描、按索引点查 |
| 结构模型 | 文档模型，商品/地址内嵌，免 JOIN | 宽表 + 列族，按列族裁剪 IO |
| 写入特征 | 高频更新（状态流转），维护 4 个索引 → 写放大高 | 归档后只增不改，顺序追加 → 写放大低 |
| 查询优势来源 | 二级索引灵活、聚合管道在内存中完成 | RowKey 有序 → 范围扫描为顺序 IO；BLOOMFILTER 加速点查 |
| 查询劣势 | 大范围扫描 + 排序易触发内存排序，数据量大时劣化快 | 多条件组合查询需预设计 RowKey 或额外索引表，灵活性差 |
| 定位 | **实时检索**：面向用户与客服的交互式查询 | **离线存储**：面向对账、审计、周期性统计 |

**一句话总结分工依据**：**查询模式决定存储选型**。热数据的查询是"条件灵活、结果集小、延迟敏感"，由二级索引 + 文档模型胜出；冷数据的查询是"条件固定、结果集大、吞吐敏感"，由有序 RowKey + 列族裁剪胜出。

### 5.2 30 天分界线的确定依据

分界线并非随意选取，而是由**访问频率随订单年龄的衰减曲线**决定的：

- 订单创建后 30 天内，会经历支付、发货、收货、售后等环节，用户与客服的查询高度集中在「订单列表」「订单详情」「物流状态」，是全部查询量的主要来源。
- 超过 30 天后，订单通常已完成且过了退换货周期，查询频率骤降为偶发的对账、审计、年度统计。

因此 30 天是一个**收益/成本平衡点**：
- 分界线太短（如 7 天）→ 归档任务频繁触发，跨库联合查询（A9）命中两库的概率大增，用户查询延迟上升。
- 分界线太长（如 90 天）→ MongoDB 中堆积大量冷数据，内存与索引体积膨胀，热查询性能被拖累，混合存储的意义被削弱。

设计上把该阈值做成**可配置参数**（`archive.cutoff.days=30`），便于在实验中调整并观察两库数据量与查询性能的变化。

### 5.3 数据流向

```
                    ┌──────────────────────────────┐
                    │     订单写入（生成/接入）      │
                    └───────────────┬──────────────┘
                                    │ orderTime ∈ 近30天
                                    ▼
                    ┌──────────────────────────────┐
                    │  MongoDB: order_real_time    │  热数据 / 实时检索
                    │  索引: uk_order_id            │
                    │        idx_user_time          │
                    │        idx_status_time        │
                    │        idx_goods_time         │
                    └───────────────┬──────────────┘
                                    │ 归档任务（定时/手动）
                                    │ 1. 查 orderTime < now-30d
                                    │ 2. 批量写 HBase 主表 + 索引表
                                    │ 3. flush 成功 ✅
                                    │ 4. 才 deleteMany(Mongo 源文档)
                                    ▼
                    ┌──────────────────────────────┐
                    │  HBase: order_history        │  冷数据 / 离线存储
                    │         order_history_idx    │
                    └──────────────────────────────┘

   查询路径：
     A1  ──► 先查热库；未命中 → 查 HBase 索引表 ID# → 主表 Get
     A2~A5 ─► 仅热库
     A6~A8 ─► 仅冷库
     A9  ──► 热库 ∪ 冷库，按 orderId 去重后按 orderTime 倒序归并
```

### 5.4 跨库一致性策略

混合存储不引入分布式事务（实验环境也不具备条件），改为**单向、幂等、可重试**的最终一致性模型：

| 策略 | 做法 | 解决的问题 |
|---|---|---|
| **写入顺序** | 严格「先写 HBase（主表 + 索引表）并 `flush()` 成功 → 再删 MongoDB 源文档」 | 任何环节失败，源数据仍在热库，重跑即可，绝不丢数据（C4） |
| **幂等性** | HBase 侧 `Put` 是覆盖语义，以 RowKey（含 `orderTime` 与 `orderId`）为主键，同一订单重复归档结果完全一致 | 任务中断后可直接重跑，无需记录断点 |
| **批次控制** | 每批 2000 条，批内原子推进；任一批失败仅回滚该批的删除动作 | 避免大批量长事务，失败影响面可控 |
| **迁移窗口内的重复读** | 在"已写 HBase、未删 Mongo"的窗口内，A9 联合查询可能同时命中两库的同一条订单 | 联合查询结果**必须按 `orderId` 去重**（以 HBase 版本为准，因其为归档后的最终形态） |
| **缺失读的兜底** | A1 按订单 ID 查询时，先查热库，未命中再查冷库 | 归档完成后热库立即无此订单，避免"查询返回空"的假象 |

## 7. 设计方案合理性论证

### 7.1 为什么用两个数据库而不是一个

| 如果只用 MongoDB | 如果只用 HBase |
|---|---|
| 历史数据无限累积，索引体积与内存占用持续增长；大范围扫描 + 排序需要把大量文档拉进内存，性能随数据量快速劣化；冷数据占用昂贵的在线存储资源 | 多条件组合查询（A2~A5）无法在不预先设计 RowKey 的情况下高效完成，每个新查询条件都需要新建一张索引表；聚合统计能力弱，需自行遍历累加 |

**结论**：两个库的短板恰好互为对方的长板。MongoDB 缺"大批量顺序扫描与低成本长期存储"，HBase 缺"灵活的多条件实时检索"。混合架构让热数据留在具备灵活索引与聚合能力的 MongoDB，冷数据沉到擅长顺序扫描与水平扩展的 HBase，各自承担最擅长的负载。

### 7.2 设计决策与收益对照

| 设计决策 | 放弃的东西 | 换来的收益 |
|---|---|---|
| 冷库 RowKey 用「倒序时间戳 + orderId」 | 无法直接按 orderId 点查 | 时间范围扫描与月度统计直接命中 RowKey 前缀（G2/G4） |
| 冷库引入二级索引表 | 写入时多维护一张表、额外存储约 40% | 按订单 ID / 用户 ID 的等效点查不退化为全表扫描（G3） |
| 冷库列族按访问模式分 3 组、`status` 冗余 | 状态更新需写两个列族 | 聚合与全字段扫描两条路径都不产生跨列族补读 |
| 热库商品/地址内嵌 | 单文档变大 | 一次查询返回订单全貌，免 JOIN |
| 热库金额用 Decimal128 | 聚合需显式类型转换 | 金额精确无浮点误差 |
| 热库不设 TTL | 需自行实现清理逻辑 | 数据不丢（C4），生命周期可控可观测 |
| 归档采用「先写冷库后删热库」+ 幂等 | 迁移窗口内需按 orderId 去重 | 任意时刻中断都可安全重跑，无数据丢失 |
| 冷库按时间预分区而非加盐 | 写入热点未被打散 | 范围扫描保持连续、单一 Region 命中 |

### 7.3 与实验要求的对应关系

| 实验要求 | 本设计的回应 |
|---|---|
| 明确核心业务字段，可扩展 | §2 统一字段字典，含 `coupon`、`channel`、`expressNo`、`goods.category` 扩展字段 |
| HBase 表名、列族（info/pay/logistics）、列定义 | §3.1、§3.2 |
| 重点优化行键设计，采用"订单 ID"或"下单时间+订单 ID"，确保唯一且便于批量扫描 | §3.3，在"下单时间+订单 ID"基础上改进为**倒序**时间戳，并给出四种候选方案的对比论证 |

## 8. 容量与性能预估

### 8.1 容量预估（10 万条基准）

| 存储 | 数据量 | 实际占用 | 说明 |
|---|---|---|---|
| MongoDB `order_real_time`（约 6 万条） | ≈ 42 MB | ≈ 45 MB（含 4 个索引） | 单文档约 700 B × 6 万；索引额外约占数据量的 5%~10% |
| HBase `order_history`（约 4 万条） | ≈ 32 MB | ≈ 32 MB | 列族不压缩（`COMPRESSION=NONE`，原因见 §3.4）；若环境支持 Snappy 可降到约 12 MB |
| HBase `order_history_idx` | ≈ 8 MB | ≈ 8 MB | 每订单 2 行索引 |
| **合计** | | **≈ 85 MB** | 单机环境完全无压力 |

### 8.2 查询代价预估

| 访问模式 | 理论代价 | 预期量级 |
|---|---|---|
| A1 按订单 ID（热库） | 1 次索引查找 + 1 次文档读取 | < 10 ms |
| A1 按订单 ID（冷库） | 2 次 RPC（索引表 Get + 主表 Get），BLOOMFILTER 减少无效 IO | 10~30 ms |
| A2 按用户查（热库） | `idx_user_time` 前缀定位，返回集小 | < 20 ms |
| A4 时间范围 + 商品 ID | `idx_goods_time` 等值前缀 + 范围扫描 | < 30 ms |
| A5 近 7 天聚合 | 覆盖式索引扫描 + 内存分组 | < 100 ms |
| A6 按时间范围扫描（冷库） | 顺序读 RowKey 连续区间，`caching=500` 减少 RPC | 10 万级全量扫描秒级 |
| A7 按月统计 | 单月区间 ≈ 8000 行 ≈ 2.5 MB 顺序读 | < 1 s |
| A8 按用户查（冷库） | 索引前缀 Scan + 批量 Get 主表（N 次 RPC 合并为批量） | 与结果条数线性相关 |
| A9 联合查询 | 热库 + 冷库各一次查询，再内存归并去重排序 | ≈ 两者之和 + 归并开销 |

> 上表为设计阶段的量级预估，用于指导实现时的调优方向；实测值需在实验的性能测试阶段记录并与预估对照，偏差部分正是分析优化的切入点。

## 9. 设计权衡与备选方案

| 备选方案 | 内容 | 优点 | 缺点 | 采纳结论 |
|---|---|---|---|---|
| B1 | 冷库单表，RowKey 直接用 `orderId` | 结构最简单，A1 一次 Get 命中 | A6/A7 时间范围扫描退化为全表 Scan，直接违反 G2 | ❌ 不采纳 |
| B2 | 冷库 RowKey 用**正序**时间戳 + orderId | 区间映射直观（`start=from`, `stop=to`），扫描结果时间升序 | A2/A3/A8 要求倒序返回，HBase 无高效逆序 Scan，须客户端排序或缓存全量结果 | ❌ 不采纳，采用倒序（S3） |
| B3 | 冷库 RowKey 加哈希盐前缀（16 桶）打散热点 | 写入负载在写放大场景下更均衡 | 时间范围扫描必须拆成 16 段再归并，读路径复杂度显著上升；10 万级数据无热点压力 | ⚠️ 暂不采纳，作为水平扩展时的演进方案记录在案 |
| B4 | 用 HBase Coprocessor（Endpoint/Observer）实现二级索引 | 索引维护对应用透明，强一致 | 需部署协处理器代码，调试与故障排查成本高；实验环境不便于部署（C2） | ❌ 本实验不采纳 |
| B5 | 索引表拆成 `order_history_idx_id` 与 `order_history_idx_user` 两张表 | 两类索引的 TTL、压缩策略、Region 数可独立配置 | 表数量增加，写入需维护两张额外表，运维与代码复杂度上升 | ⚠️ 合并为一张表（§3.6），若两类索引量级差异悬殊再拆 |
| B6 | 用 MongoDB Change Streams 订阅变更实现准实时归档 | 归档延迟低（秒级） | 需要副本集/分片集群，实验环境为单节点；错误恢复语义更复杂 | ⚠️ 作为优化方向记录，本实验用定时任务 |
| B7 | 热库金额用 `double` | 聚合可直接 `$sum`，写法简单 | 浮点误差在汇总统计时累积，金额不精确 | ❌ 不采纳，用 Decimal128 |
| B8 | 热库设置 TTL 自动过期 | 无需实现清理逻辑 | 与归档任务竞争，失败时数据永久丢失（违反 C4） | ❌ 不采纳（§4.5） |
| B9 | 冷库把 `status` 只放 `pay` 列族 | 少写一个列族，节省少量空间 | A6 全字段扫描时若需状态需跨列族读；且 `logistics` 列族的语义完整性受损 | ❌ 不采纳，采用双列族冗余 |
| B10 | 冷库对 `info`/`pay`/`logistics` 再细分更多列族 | 列裁剪更精细 | 列族数增加导致 MemStore 与 Flush 次数成倍增长，小文件问题突出 | ❌ 不采纳，3 个列族为合理上限 |

## 10. 设计要点速查

1. 冷库 RowKey = `19 位倒序毫秒时间戳 | orderId` —— 时间范围扫描命中前缀 + 最新订单优先。
2. 冷库 RowKey 无法直接按 orderId 点查 → 索引表 `ID#<orderId>` / `U#<userId>#<倒序时间戳>#<orderId>`，写入方同批维护。
3. 冷库 3 个列族按访问模式分组，`status` 双列族冗余；`VERSIONS=1`、`TTL` 不设、`BLOOMFILTER=ROW`、`COMPRESSION=NONE`（本环境 Hadoop 未编译 Snappy 支持，见 §3.4）。
4. 冷库按月份预分区，不打盐——范围扫描必须保持连续。
5. 热库商品与地址内嵌，一次查询拿到订单全貌；金额用 `Decimal128`；4 个索引全部遵循 ESR 原则。
6. 热库**不设 TTL**，30 天前的数据只由归档任务在冷库写入成功后显式删除。
7. 归档遵循「先写冷库 → 成功 → 再删热库」，靠 HBase 的覆盖写实现幂等重跑。
8. 联合查询必须按 `orderId` 去重，因为迁移窗口内两库会短暂同时存在同一订单。
9. 分界阈值 30 天可配置，依据是订单访问频率随年龄的衰减曲线，而非经验拍定。
10. 每个设计决策都对应一条明确的访问模式（§6.1 可追溯性矩阵），无孤立设计。
